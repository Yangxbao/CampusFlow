## 二、GC 算法与收集器谱系（原理铺垫）

**四种基本算法：**
1. **标记-清除**：标记可达对象，清除不可达。有碎片、效率一般；
2. **标记-复制**：存活对象在 Eden/Survivor 间复制，无碎片、天然压缩；适合新生代（98% 对象朝生夕死）；
3. **标记-整理**：存活对象向一端移动，无碎片；适合老年代，移动对象成本高；
4. **分代收集**：以上算法按代组合（新生代复制 + 老年代标记整理/清除）。

**可达性分析**：从 GC Roots（线程栈帧、静态变量、JNI 引用、活跃线程、同步锁等）出发标记。
Java 不用引用计数（循环引用无法处理）。

**收集器谱系（JDK17 视角）：**
```
串行:  Serial / Serial Old              单线程，客户端小内存
并行:  Parallel Scavenge / Parallel GC  吞吐优先，JDK8 默认
并发:  CMS (JDK9 废弃 → JDK14 移除，JDK17 已不存在)
       G1  (JDK9+ 默认)  Region 化分代 + 并发标记 + 增量回收
       ZGC (JDK15 生产)  着色指针 + 读屏障，亚毫秒停顿
       Shenandoah (OpenJDK, 非 Oracle 构建无)
```

**CMS 的历史定位（面试高频）**：CMS（Concurrent Mark Sweep，老年代收集器）是最早的
"并发"收集器——标记与清理大部分与应用并发执行，目标是降低停顿。
步骤：初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除。
缺陷：① 标记-清除算法产生碎片，碎片过多触发 Full GC（Serial Old 整理，停顿巨大）；
② 浮动垃圾（并发期间新产生的垃圾只能下次收）；③ 对 CPU 敏感；
④ Concurrent Mode Failure（并发回收赶不上分配）。
JDK9 因维护成本废弃（JEP 291），**JDK14 彻底移除（JEP 363）——JDK17 里 `-XX:+UseConcMarkSweepGC`
会直接报错启动失败**。G1 全面取代 CMS。

## 三、实验 1：GcLogLab

### 3.1 源码要点

```java
for (int i = 0; i < ALLOC_PER_ROUND; i++) {
    byte[] obj = new byte[OBJECT_SIZE];    // 1KB，70%+ 立即变垃圾
    allocated += obj.length;
    if (i % 3 == 0) {
        survivors[i % SURVIVOR_SLOTS] = obj;   // 1/3 进轮转存活列表（跨 Young GC）
    }
}
if (r % 10 == 9) java.util.Arrays.fill(survivors, null);   // 定期批量死亡
```
统计口径：运行前后读 `GarbageCollectorMXBean.getCollectionCount()/getCollectionTime()` 增量。

```bash
     -Xlog:gc*,gc+heap=debug:file=gc_demo.log:time,uptime,level,tags \
     -cp target/classes com.campusflow.lab.jvm.gc.GcLogLab
```

### 3.4 JDK17 统一日志 -Xlog 速查

```text
语法: -Xlog:<tag-set>[+tag...][*[...]]=<level>[:<output>[:<decorators>[:options]]]
-Xlog:gc                                  只看 GC 基本行
-Xlog:gc*                                 全部 gc 标签（最常用）
-Xlog:gc*:file=gc.log:time,uptime,level,tags   写文件 + 装饰字段
-Xlog:gc+heap=debug                       堆变化明细
-Xlog:gc+humongous=debug                  G1 大对象分配
-Xlog:gc+metaspace=trace                  元空间分配/卸载
轮转: filecount=5,filesize=20m
```
JDK8 的 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:` 在 JDK9+ 已移除，
统一由 `-Xlog` 接管（decorator：time/uptime/level/tags/pid/tid 等）。

## 四、实验 2：GcCompareLab（G1 vs ZGC）

### 4.1 对比方法

收集器在 JVM 启动时确定，无法在同一 JVM 内切换 → **同一负载程序跑两遍**，
分别 `-XX:+UseG1GC` 与 `-XX:+UseZGC`，对比三组数字：
分配速率（吞吐基线）、GC 总耗时占比（吞吐损失）、平均/最大暂停（尾延迟）。
程序内近似测量：`com.sun.management.ThreadMXBean.getThreadAllocatedBytes()` 测真实分配字节；
`GarbageCollectorMXBean.getCollectionTime()` 增量 ÷ 墙钟 = GC 时间占比。

### 4.2 真实运行输出（同一负载 800MB，-Xms256m -Xmx256m）

G1：


**读数解读（真实数据说明近似测量的局限）**：
- 分配速率两者一致（800MB 负载相同）；
- ZGC 的"GC 时间占比"偏高且墙钟更长——本负载太短（百毫秒级），MXBean 毫秒粒度统计
  与 ZGC 并发阶段（不入 STW 口径）的统计方式叠加造成失真；**结论必须以 -Xlog:gc* 的
  Pause 行分布为准**（G1 的 Pause Young 行尾毫秒数 vs ZGC 的 "Pause Mark Start/End" 系列，
  ZGC STW 阶段只有亚毫秒级）；
- 教学要点：小负载下 MXBean 近似只能看数量级；真正的对比要跑数分钟级负载再统计 Pause 行 P50/P99。

### 4.3 原理对比与适用场景

| 维度 | G1 | ZGC |
|---|---|---|
| 核心机制 | Region 化分代 + SATB 并发标记 + 增量回收(Mixed GC) | 着色指针(Colored Pointers) + 读屏障(Load Barrier) |
| 停顿目标 | 可设 `-XX:MaxGCPauseMillis=200`，随堆增长变差 | <1ms，不随堆大小增长（JDK17 实测常为 0.1~0.5ms） |
| 碎片 | Region 间复制整理，基本无碎片 | 并发转移整理，无碎片 |
| 吞吐损失 | 小 | 略高（读屏障 ~10-15% 开销、内存多 5%+ 元数据） |
| 堆推荐 | 4GB~32GB 通用 | 8GB~16TB、尾延迟敏感场景 |
| 适用 | 平衡吞吐与延迟的通用服务（大多数业务） | 大堆低延迟：实时风控、交易、网关 |

**面试要点：ZGC 为什么停顿不随堆变大？**
标记/转移/重定位全部并发执行，STW 只发生在"根扫描"与极短的同步点；
靠 64 位指针中的 4 个颜色位 + 读屏障实现转移期间应用线程自愈式指针更新。
代价是读屏障开销与转移并发期吞吐下降。

## 五、常见面试追问与参考答案

**Q1：Minor GC、Major GC、Full GC 的区别？**
A：Minor GC 只收新生代（STW 短）；Major GC 是 CMS/老年代回收的历史叫法（G1 语境里
常混指 Old GC）；Full GC 收整堆+元空间（STW 最长，通常伴随压缩/整理）。
G1 里表现为 Pause Young / (Pause Old/Mixed) / Pause Full；Full GC 在 G1/ZGC 都是"兜底"，
出现即说明并发回收赶不上分配速度，要重点排查。

**Q2：对象什么时候进老年代？**
A：① 年龄阈值（默认 15，`-XX:MaxTenuringThreshold`，动态判据：Survivor 中同龄对象
超过一半则该年龄及以上直接晋升）；② 大对象直接进 Old（G1 humongous：对象 > Region 50%）；
③ 动态年龄判定；④ Survivor 空间不足时的提前晋升（担保机制）。

**Q3：G1 的 Mixed GC 是什么？**
A：并发标记 cycle 结束后，G1 选中"垃圾比例高"的老年代 Region 与新生代一起回收
（`Pause Young (Concurrent Start) → Remark → Cleanup → Pause Mixed`），
`-XX:InitiatingHeapOccupancyPercent`(IHOP, 默认45%) 触发并发标记，
按 `-XX:G1HeapWastePercent`/`G1MixedGCLiveThresholdPercent` 控制参与度。
本质是"增量式老年代整理"，避免一次 Full GC。

**Q4：什么情况下会 Full GC？如何避免？**
A：G1 场景：① 转移失败(to-space exhausted)晋升失败；② humongous 分配失败触发压缩；
③ 元空间满；④ `System.gc()`；⑤ 大对象潮涌导致 Old 回收速度 < 分配速度。
避免：控制大对象（拆分/缓存复用）、合理 IHOP（JDK8u101+ 支持自适应）、
限流批处理、预留堆空间（-Xmx ≤ 容器内存 75%）。

**Q5：CMS 为什么被移除？JDK17 还能用吗？**
A：JDK9 废弃（JEP 291，维护成本高、依赖 SA 相关组件），JDK14 移除（JEP 363）。
JDK17 中 `-XX:+UseConcMarkSweepGC` 直接 "Unrecognized VM option" 级报错启动失败
（实际提示 Unrecognized/ignorable），CMS 的定位被 G1 完全取代。
面试时强调：给老系统做 JDK 升级评估时，CMS 参数必须清理，这是常见升级障碍。

**Q6：-Xlog:gc* 输出里你最看哪几行？**
A：`Pause ... <前堆>-><后堆>(<容量>) <毫秒>`：看停顿分布与回收率；
`gc,heap` 的 before/after 看 Region 用量；`gc,metaspace` 看类卸载；
`To-space exhausted`、` humongous allocation` 关键字排查 Full GC 诱因；
再用 `gc+ergo` 看 G1 的自适应决策。

**Q7：如何用 gc.log 计算 P99 停顿？**
A：`grep 'Pause' gc.log | awk '{print $NF}'`（去掉 ms 单位）排序后取 99 分位；
或用 GCEasy / gctoolkit 解析。生产上配合 `-Xlog:gc*:file=...:filecount=5,filesize=20m` 轮转防膨胀。
