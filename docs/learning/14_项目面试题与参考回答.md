## 一、高并发报名核心（必问区）

### Q1. 高并发报名怎么防止超卖？

**错误示范**："用了 Redis 分布式锁，抢到锁的人再扣库存。"
（锁能防并发，但每次抢锁串行化整个活动，吞吐崩塌；且锁不是唯一约束，仍有边界。）

**满分答法（按真实代码链路，四层防线）**：
1. **Lua 原子预留**（`lua/reserve.lua` + `StockRedisService.reserve`）：校验+扣减+登记一次原子执行——
   元数据校验 → 时间窗 → 用户限流 INCR/EXPIRE → SISMEMBER 一人一单 → GET/DECR 库存 → SADD 成员 + SET 预留状态。
   脚本头注释写明为什么不用 GET+DECR 两步："两条命令间存在并发窗口，1000 个并发同时 GET 到 stock=1
   再各自 DECR 会变成 -999（超卖）；Redis 单线程执行脚本，检查与扣减之间不会插入其他命令"；
2. **MQ 异步落库**（`RegistrationTxService.persistReservation`：预留记录+发件箱消息同事务），
   写 MySQL 不在洪峰路径上；
3. **MySQL 唯一约束**（`uk_activity_user`）：消费端 `confirmRegistration` 撞
   DuplicateKeyException 转幂等分支——绕过任何缓存直接写库也不可能重复；
4. **补偿兜底**（`CompensationScheduler`）：预留超时释放 + 每 5 分钟库存对账
   （`stockReconcile` 以 DB 为权威口径修复漂移并审计）。
   **压测证据**：场景 A 999 请求 0 错误，DB 恰好 100 条、Redis 库存 0、confirmed_count=100。

### Q2. 为什么用 Lua 而不是"分布式锁 + 扣库存"或纯数据库乐观锁？

**错误示范**："Redis 分布式锁最安全，所以都用锁。"
**满分答法**：三条路对比——分布式锁把 1000 并发串行成 1000 次锁竞争，QPS 崩塌且锁服务成为单点；
DB 乐观锁（UPDATE ... WHERE stock>0）每次请求都打 DB，洪峰下连接池与行锁先崩；
Lua 把"校验+扣减"合成 Redis 内原子操作，**只有满员/重复/限流的拒绝走 Redis，
成功的才异步写 DB**——场景 A 的 997 个请求平均 2.3ms、P99=5ms 就是不碰 MySQL 的直接结果。
分布式锁在本项目用于"低频必须串行"的场景（库存预热/候补晋级/定时任务），各归其位。

### Q3. 消息怎么做到不丢？（发送/存储/消费三段）

**错误示范**："RocketMQ 自带可靠性，没做额外处理。"
**满分答法**（对应 `MessageDeliverService`）：
1. **生产端**：本地消息表（事务性发件箱）——业务事务内 insert `message_deliver(status=NEW)`，
   事务提交后立即 `trySendDeliver` 同步发送并等 SEND_OK；发送失败置 FAILED + **指数退避**
   （`baseSeconds * 2^retry`，上限 6 次方）由 `messageRetry` 任务每 15s 重投；
   消息丢失风险只剩"DB 记录丢失"，而 DB 是持久化的；
2. **存储端**：同步刷盘/主从配置在 Broker 侧，本地消息表提供对账依据；
3. **消费端**：`RegistrationConfirmConsumer` 返回 CONSUME_SUCCESS 才算消费完成；
   业务异常返回 RECONSUME_LATER 重试，达到 `consumerMaxReconsume`（5 次）转**补偿任务**
   （业务级死信处理，`CompensationTaskService`）确认消费防堆积；
   消费成功回调 `confirmConsumed` 把本地消息表置 CONFIRMED，形成**投递-消费闭环**，
   预留恢复任务对账时能发现"消息发出去了没消费掉"的情况。

### Q4. 为什么用本地消息表而不是 RocketMQ 事务消息？

**错误示范**："事务消息更高级，肯定选它。"
**满分答法**（`MessageDeliverService` 类注释原文答）：
事务消息适用"只关心 DB 提交与发送原子性、能接受半消息反查"的场景；
本地消息表的优势是**投递轨迹持久化**（对账/审计/管理端可视化消息状态）+
重试策略完全自主（指数退避节奏、重试上限自己定）。本项目两个都要，主链路用本地消息表；
事务消息方案留作集成测试对比实验（进阶练习 16-2）。
另外事务消息的反查逻辑要实现 checkLocalTransaction，状态判定逻辑和本地消息表殊途同归，
还要维护额外的半消息状态机。

### Q5. 消费端幂等怎么设计的？

**错误示范**："用 Redis setnx 记录 msgKey 就幂等了。"
**满分答法**（`MessageConsumeLogService.tryBeginConsume` 三层）：
L1a Redis **认领锁**（SETNX 60s TTL）——并发重复消息只有一个线程进入处理，
注释里的关键推理："Broker 对业务键相同的两条独立消息不做去重，并发投递时 DB 唯一约束
存在检查-插入竞态窗口"；L1b Redis processed 标记（成功后写，TTL 24h）——已处理快速跳过；
L2 DB `uk_msg_group` 唯一约束——Redis 重启/淘汰后的最终防线。
失败重试语义：markFailed 后允许重试，成功后 status=1 永久拦截。
底层业务还有第二层幂等（confirmRegistration 的唯一约束 + 状态 CAS），双保险。

### Q6. 消息重试达到上限怎么办？死信怎么处理？

**错误示范**："进死信队列，人工处理。"（只说概念没说方案）
**满分答法**：三层——① RocketMQ 客户端重试 `maxReconsumeTimes=5`（Broker 延迟级别递增投递）；
② 达到上限**不进裸 DLQ**，业务代码主动转补偿任务表（`handleFailure` 里
`compensationTaskService.createTask(TYPE_REGISTRATION_CONFIRM, msgKey, body)`）并确认消费防堆积；
③ 补偿任务由 `CompensationTaskService.processDueTasks` 扫描执行（uk_biz_key 幂等创建、maxRetry=5、
nextRetryTime 退避）。比裸 DLQ 强在：处理逻辑与业务同步演进、有重试节奏、有对账入口。

### Q7. 候补队列怎么设计的？

**错误示范**："数据库一张表按时间排序，轮询第一个。"
**满分答法**（Redis ZSet 权威 + DB 持久化双轨，`WaitlistService`）：
- **入队**：`ZADD NX`（addIfAbsent）原子防重复入队 + 排队号 INCR（`activityWaitlistSeq`）+
  DB `waitlist` 表 uk_activity_user 唯一约束兜底；score=入队时间戳保证真实顺序；
- **出队**：取消释放名额后 `WaitlistPromoteService.tryPromoteNext` 在**活动级 Redisson 锁**内循环
  `waitlist_serve.lua`：ZPOPMIN 弹队首 + DECR 库存 + SADD 成员 + 写预留，一个 Lua 原子完成；
- **确认**：晋级者 30 分钟内确认（`waitlist-confirm-minutes`），超时 `waitlistTimeout` 任务
  释放名额（Lua SREM 幂等）自动晋级下一位；
- **兜底**：`waitlistBackfill` 每 60s 巡检"库存>0 且队列非空却无人晋级"的漏晋情况；
- DB 记录作用：重启后可重建队列 + 审计；Redis 只存"排队顺序"这一易失状态。

### Q8. Redis 和 MySQL 的数据一致性怎么保证？（库存为例）

**错误示范**："每次改 Redis 同时改数据库就行。"（双写不一致的经典错误）
**满分答法**：方案是**"Redis 权威扣减、DB 异步对账"**（`StockRedisService` 类注释原文）——
报名洪峰只动 Redis；DB 侧 confirmed_count 由消费端事务维护为对账口径；
`CompensationScheduler.stockReconcile` 每 5 分钟按 `capacity - 有效报名数` 重算期望值，
漂移 ≥ 阈值（reconcile-threshold=3）就按 DB 权威口径重建 Redis 并写审计
（bizKey 幂等 `RECONCILE-activityId-时间窗`）+ 创建告警任务。
活动变更（发布/容量调整/取消）走 Cache Aside：锁内重算预热 + evictStockKeys。
**关键认知**：这是最终一致，不是强一致；洪峰期间的瞬时偏差可接受，对账兜底收敛。

### Q9. 缓存穿透/击穿/雪崩，你怎么防的？

**满分答法**（全部有真实代码）：
- **穿透**（查不存在的 ID）：Redisson RBloomFilter（`BloomFilterService`，expected=100000、
  fpp=0.01）前置拦截 + `MultiLevelCacheService.get` 对 DB 空结果缓存空值占位（TTL 60s）；
- **击穿**（热点 key 过期瞬间打 DB）：本地 Caffeine 30s TTL 先挡一层；库存预热用
  @DistributedLock（`activity:publish:` / lockStockPreload）防并发重复预热；
- **雪崩**（大量 key 同时过期）：TTL 加了天然错峰——活动结束时间+7 天（按活动维度散开），
  本地缓存 30s 与 Redis 30min 不同的过期粒度。

### Q10. 布隆过滤器误判怎么办？（追问 Q9）

**错误示范**："误判就不处理了，概率很低。"
**满分答法**：先讲原理——位数组+多 hash，**只会把"不存在"误判为"可能存在"（放行），
绝不会把"存在"误判为"不存在"（漏判）**，所以作为穿透防线是安全的：误判的代价只是
放行一个不存在的 ID 到缓存/DB，由空值占位兜底（`MultiLevelCacheService` 返回 null 前写 60s 空值）。
已知局限（`BloomFilterService` 注释原文）：不支持删除——活动取消后仍会放行查询，空值兜底；
Redis 重启丢失——启动 tryInit 幂等初始化 + 全量重建方法 `rebuildActivityBloom`。
参数 fpp=0.01、expected-insertions=100000 是容量预估下内存与误判率的折中。

### Q11. 多级缓存怎么保证多实例一致？

**错误示范**："每个实例自己维护缓存就行。"（多实例各改各的，脏读到天荒地老）
**满分答法**：写路径 = 先更新 DB → 删除两级缓存（**Del 不是 Update**，避免并发写覆盖与双写不一致）
→ 发广播 MQ（`TOPIC_CACHE_EVICT`）；`CacheEvictConsumer` 用 **BROADCASTING 广播模式**
（`MqConsumerFactory` 注释：缓存失效类 Topic 每个实例都消费）让各实例只失效本地 Caffeine。
兜底：本地 TTL 仅 30s，广播丢失脏读窗口也被限制在 30s 内——设计上接受秒级脏读
（广播模式消费失败不重投，这是明示的取舍）。

### Q12. 报名状态机是怎么设计的？

**满分答法**（`RegistrationStatus` + `RegistrationTxService`）：
```
确认链路: RESERVED(0,确认中) -> CONFIRMED(1) -> CHECKED_IN(2)
取消链路: CONFIRMED -> CANCELLED(3)  (行保留，可复用同侧行重新报名)
异常链路: RESERVED -> CONFIRM_FAILED(4)  (补偿释放名额，终态)
```
状态推进全部 CAS：取消用乐观锁 version；确认用唯一约束+幂等回迁（取消后重新报名复用同一行，
`idempotentConfirm`）；每次迁移写 `registration_state_log`（from/to/reason/operatorId）——
**状态机 + 状态日志 = 任何数据异常都能追溯到操作序列**。occupiesStock() 判定哪些状态占名额。

### Q13. 定时补偿任务多实例会重复执行吗？

**满分答法**：`CompensationScheduler` 六个任务全部 `lockService.tryRun(lockKey, task)`
（Redisson tryLock(0) 抢锁，抢不到说明另一实例在跑，静默返回）。锁 Key 集中在
`RedisKeyConstants.lockCompensationJob(jobName)`。**幂等才是根治**：任务内操作全部幂等
——Lua SREM 幂等释放、DB 状态 CAS、审计 bizKey 唯一、补偿任务 uk_biz_key。
所以设计原则是"锁防重入，幂等防叠加"，缺一不可。

### Q14. 签到怎么防止两个管理员同时扫码重复核销？

**满分答法**（`CheckinService.scan` 注释原文三层）：① Redis SETNX 一次性令牌
（`campusflow:checkin:once:{tokenHash}`，TTL 5min）快路径；② DB 事务内 CAS：
token status=0→1 与 registration status=1→2 同事务推进，任一失败整体回滚；③
`checkin_record uk_registration` 唯一约束兜底。防伪造：明文 token 只在签发时返回一次，
DB 只存 SHA-256 摘要——截获二维码内容也无法反推他人凭证。
集成测试 `CheckinConcurrencyIT`（10 并发核销同一凭证）验证仅 1 次成功。

### Q15. 用户级限流为什么放 Lua 里？固定窗口有什么问题？

**满分答法**：放 Lua 是因为限流 INCR/EXPIRE 必须与库存扣减在同一原子块里，
否则"限流通过但库存判断已过期"产生竞态。固定窗口问题：窗口交界突刺（两窗口交界
可能放行 2×limit）——`RateLimiterService` 注释原文承认这一点并给出升级路径
（ZSet 滑动窗口 / Redisson RRateLimiter 令牌桶），本项目业务量下固定窗口足够
（参数 8 次/10s，场景 B 992 次拦截证明有效）。**先讲清边界再讲升级方案 = 加分。**

## 二、分布式锁与 Redis（高频追问区）

### Q16. Redisson 看门狗是什么原理？

**错误示范**："就是自动续期的定时任务。"（太浅）
**满分答法**：`lock.tryLock(waitTime, unit)` **两参形式不传 leaseTime** 时启用 watchdog：
默认锁 TTL 30s，Redisson 客户端每隔约 1/3（10s）检查业务是否还在执行，在则重置 TTL 回 30s。
解决的问题是：**业务执行时间 > 锁 TTL 时锁提前过期，另一客户端拿到锁，业务并发且原持有者
解锁时误删别人的锁**。项目实现：`DistributedLockAspect` 中 leaseTimeMillis<=0 走看门狗模式；
显式传 leaseTime 则看门狗失效（注释：适合执行时间确定的短任务，且必须保证 leaseTime > P99 耗时）。
注意：看门狗要求业务代码与解锁在同一 JVM（客户端存续），进程被 kill -9 则锁最终会自然过期释放。

### Q17. 锁误删问题怎么防？

**满分答法**（`DistributedLockAspect` 类注释三条）：① 看门狗防"业务未完成锁先过期"；
② Redisson 锁值带客户端唯一 ID（UUID:threadId），删除前校验持有者——
**`lock.isHeldByCurrentThread()` 校验后才 unlock**（代码里 finally 块就是这个写法）；
③ 显式 leaseTime 场景存在残余窗口，靠业务幂等兜底（如预热幂等、补偿幂等）。
自研 setnx+expire 的锁在这三点上都要手写 Lua（值校验+删除原子），所以直接用 Redisson。

### Q18. Redis 主从切换时锁会怎样？（Redlock 了解吗）

**满分答法**：单实例 Redisson 锁在主节点写入、异步复制到从节点，主挂了 failover 到从，
**极端情况下锁状态丢失**，两个客户端可能同时持锁。缓解：本项目的锁保护场景全部
幂等兜底（预热/晋级/补偿），锁只是效率工具不是正确性工具——正确性由 Lua 原子 +
DB 约束保证。Redlock（多数节点过半成功）能降低该概率但争议大（Martin Kleppmann 与
antirez 的论战），分布式系统里"锁 + 幂等"才是工程正解，纯靠锁保证正确性是错误认知。

### Q19. 雪花算法时钟回拨怎么处理？

**满分答法**（`SnowflakeIdWorker`，项目自研实现）：结构 1 符号 + 41 时间戳 + 10 机器 ID + 12 序列
（单机每毫秒 4096 个 ID）；`nextId()` 里 `timestamp < lastTimestamp` 时：
回拨 ≤ `MAX_BACKWARD_MS`(5ms) 则 `wait(offset << 1)` 等待追平后重取；
仍回拨直接抛 IllegalStateException 拒绝生成（**宁可不发号，不发重复号**）。
同毫秒序列耗尽自旋 tilNextMillis。线程安全用 synchronized（争用极低，够用且易懂——注释原话）。
面试延伸：机器 ID 分配（配置中心/DB 表/ZK）；为什么不用 UUID（无序、索引页分裂）。

### Q20. 为什么前端拿到的雪花 ID 会错？怎么解决？

**错误示范**："没遇到过。"（说明没用雪花 ID 或没联调过）
**满分答法**：19 位 Long 超出 JS Number 安全整数 2^53-1，IEEE 754 静默舍入末几位
（真实案例 2123838677402947593 -> ...600，`JacksonConfig` 注释原文），前端拿错误 ID 回查 404。
解法：`JacksonConfig` 注册 `ToStringSerializer` 把 Long/long 全局序列化为字符串；
前端把 id 当字符串传递。这是"雪花 ID + Vue 前端"的标准解法，改动一处、全局生效。

## 三、架构与工程

### Q21. 为什么不用微服务？

**错误示范**："单体太 low 了，微服务才是先进。"（校招最忌空谈架构）
**满分答法**：反向论证——CampusFlow 是校园活动报名，团队 1 人、数据规模单库可控，
微服务的代价（分布式事务、服务发现、链路追踪、运维复杂度）远大于收益。
但项目用 **Maven 多模块做了"逻辑微服务化"**：campusflow-common（常量/错误码/工具）、
infrastructure（Redis/MQ/锁/线程池等基础设施）、business（业务域：registration/waitlist/
checkin/activity/compensation）、server（配置与装配）——依赖单向向下，
未来拆服务时按模块边界直接拆。压测证明单机 1677 QPS 读、Lua 挡流的写架构已达标。
**结论：架构选型服务规模，不为简历堆技术名词。**

### Q22. 你们的模块依赖关系怎么设计的？

**满分答法**：common <- infrastructure <- business <- server（单向依赖，无环）；
concurrency-lab / jvm-lab 独立无 Spring 依赖（纯 JDK 实验模块）。
好处：基础设施接口（StockRedisService/MessageDeliverService/RedissonLockService）
被业务层依赖而不感知具体实现；server 只做装配（GlobalExceptionHandler/JacksonConfig/
TraceIdFilter/消费者 Bean）。`application.yml` 里 `allow-bean-definition-overriding: true`
还记录了 fat-jar 嵌套 jar 双重资源扫描的真实坑。

### Q23. JWT 认证怎么实现的？和 Session 方案怎么选？

**满分答法**：`JwtAuthInterceptor`（HandlerInterceptor）解析 `Authorization: Bearer`
→ `JwtUtils.parseToken` → UserPrincipal 写入 **AuthContext（ThreadLocal）**，
`afterCompletion` 强制清理（Tomcat 线程复用防串号）；角色校验按 URI 前缀
（/admin 仅 ADMIN，/organizer 需要 ORGANIZER+）。
选型：JWT 无状态、水平扩展友好（不用共享 Session 存储）；代价是**签发后无法主动作废**，
本项目靠 24h 过期（expire-hours）+ 服务端鉴权兜底。session 方案适合需要强制踢人的场景
（配合 Redis 存 session 可即时失效）。secret 生产环境变量注入（≥32 字节）。

### Q24. 密码怎么存的？为什么 BCrypt 慢反而是优点？

**满分答法**：`UserService` 用 spring-security-crypto 的 BCrypt 存储（类注释：注册唯一性由
uk_username 兜底）。BCrypt 内置盐 + 可调 cost，故意慢（CPU 密集）——**对单次登录不可感知，
对暴力破解成本指数级**。压测场景 A 为此专门做了 setUp 预登录把登录挡在突发外
（13 讲）。对比：MD5+盐已不适合（GPU 每秒数十亿次），argon2/scrypt 是更现代的选择。

### Q25. TraceId 是怎么贯穿全链路的？

**满分答法**：`TraceIdFilter`（Order(1)）读 `X-Trace-Id` 头，无则生成 32 位 UUID
（`TraceUtils.newTraceId`），MDC.put + 响应头回传；logback pattern `%X{traceId}` 每行日志自带；
`GlobalExceptionHandler` 把 traceId 塞进 ApiResult 返回给前端；CORS exposeHeaders 让 JS 可读。
**线程复用清理**：finally 里 MDC.remove——MDC 底层是 ThreadLocal，Tomcat 线程复用不清理会串号。
Filter vs Interceptor 边界：协议层关注点（所有请求）用 Filter，MVC 业务关注点用 Interceptor。

### Q26. 乐观锁在哪用了？为什么不用悲观锁？

**满分答法**：`RegistrationDO.version` 字段 + MyBatis-Plus updateById 自动 WHERE version=?
（affected=0 即并发冲突）。用例：取消报名（并发取消只成功一次，`CancelConcurrencyIT` 验证
名额只恢复一次）、活动状态流转（approvePublish 并发审核）、签到核销。
悲观锁（select for update）在洪峰下会把 DB 连接池占满；乐观锁只在冲突时失败重试，
本项目冲突方直接幂等返回 false，无需重试循环。消费端并发插入则靠唯一约束兜底。

### Q27. @Transactional 什么情况下失效？你项目里怎么防的？

**满分答法**：最经典的是**同类自调用**（this.method() 不走代理）。
项目对策写在 `RegistrationTxService` 类注释："本类方法均带 @Transactional 且被外部类调用
（避免同类自调用代理失效）"——事务边界**集中管理在一个 TxService**，编排层
`RegistrationService` 非事务地调用它。其他失效场景：非 public 方法、rollbackFor 未设
（默认只回滚 RuntimeException，本项目统一 `rollbackFor = Exception.class`）、
传播行为误用、catch 掉异常继续走。另有一个趣味点：`RegistrationService` 用
`@Autowired(required=false) LongConsumer waitlistPromoteRunner` 函数注入解除
与 WaitlistService 的循环依赖（`WaitlistWiringConfig`）。

### Q28. 线程池怎么配置的？为什么禁止 Executors.newXxx？

**满分答法**（`ThreadPoolConfig`）：三个池七参数全显式——notifyExecutor（IO 密集 4/8，
队列 200，CallerRuns）、exportExecutor（任务少而重 2/4，队列 50，**Abort**——导出任务堆积会
OOM，直接拒绝给用户报"任务过多"）、compensationExecutor（2/4，100，CallerRuns）。
禁止 Executors 的原因（阿里规约 + 本项目理由）：newFixedThreadPool/newSingleThreadExecutor
队列无界（堆积 OOM），newCachedThreadPool 线程无界（线程数爆炸）。
细节加分项：命名 ThreadFactory（notify-worker-N 便于 jstack 定位）、
UncaughtExceptionHandler 记日志、allowCoreThreadTimeOut(true) 低峰释放、
destroyMethod 优雅关闭等存量任务完成。

### Q29. 签到凭证怎么防伪造？

**满分答法**：明文 token = UUID + 雪花 ID，**只在签发响应里出现一次**，DB 存
SHA-256(token) 摘要（`CheckinTokenDO.tokenHash`）；核销时对请求里的 token 做 SHA-256 后按摘要查——
截获 QR 内容的人无法反推出可用的明文（摘要单向）；同一报名凭证唯一、重复获取走重签发
（刷新页面拿不到旧明文，token 主键不变覆盖 hash）；一次性 SETNX 防重放。
这是"凭证型系统"（票务/核销）的通用设计。

### Q30. 为什么报名接口返回"确认中"而不是同步返回结果？

**满分答法**：`SignupResultVO(registrationId, reservationId, "PENDING_CONFIRM", ...)`——
洪峰下 DB 写入必须异步（MQ 削峰），同步落库会把 MySQL 打爆。前端拿到"受理成功"后轮询
"我的报名"列表（GET /my/registrations）确认最终状态。**这是异步化架构对 API 语义的改变**：
接口语义从"报名成功"变为"报名受理"，需要产品层面配合（前端文案 + 轮询）。
压测数据支撑：997 个请求 2.3ms 返回，100 条确认在数秒内异步完成（消息全部 CONFIRMED）。

## 四、JVM 与 JUC 快答（结合 lab 模块）

### Q31. 三种 OOM 你都见过吗？

**满分答法**：jvm-lab 全部复现过——heap space（64m 堆 31 个 1MB byte[]，G1 humongous 代价）、
Metaspace（32m 上限 5373 个动态类 + loader 强引用泄漏形态）、StackOverflow（-Xss256k 深度
16435→2307）。排查四步：VM.uptime/GC 日志 → class_histogram → thread dump 三份 →
heap dump + MAT。生产必配 HeapDumpOnOutOfMemoryError（实证过 35MB hprof 自动生成）。

### Q32. volatile 能解决什么问题？不能解决什么？

**满分答法**（`concurrency-lab/visibility/VolatileLab` 实验结论）：保证可见性（写立即刷主存、
读失效缓存行）与禁止指令重排（内存屏障）；**不保证原子性**——count++ 是读改写三步，
volatile 仍丢更新。CAS（AtomicLong）解决原子性但有 ABA（CasAbaLab 用版本戳
AtomicStampedReference 思路解决）；高竞争下 LongAdder 分段累加优于 AtomicLong。

### Q33. ThreadLocal 为什么会内存泄漏？

**满分答法**（ThreadLocalLab + ReferenceLab）：ThreadLocalMap 的 key 是弱引用（下次 GC 必回收），
value 是强引用——key 被回收后 value 悬挂，线程池线程长存则 value 永不释放。
所以**用完必须 remove**。项目两处示范：TraceIdFilter finally MDC.remove、
JwtAuthInterceptor afterCompletion AuthContext.clear——都是 Tomcat 线程复用场景下的铁律。

### Q34. 消息消费线程数怎么定的？

**满分答法**：`MqConsumerFactory` 统一创建（consumeThreadMin=5/max=20，配置化），
消费端线程池有界防失控；本地消息表让"落库慢"不阻塞上游。对比 ThreadPoolConfig 的
notifyExecutor（消费端异步通知落库 4/8 CallerRuns）：MQ 消费线程拉取消息，
DB 写入压到业务线程池，两层有界池形成背压链路。调优思路见 13 讲（20-50 对照实验）。

## 五、反问与开放题

### Q35. 这个项目你还能怎么改进？

**满分答法**（展示边界意识，说 3 个有深度的）：
① 读热扩容：活动名单查询走广播，量大后异构"activity_id 索引表"（消费 registration 变更事件）；
② 本地消息表 → 事务消息对比实验，量化运维收益；③ 接入 SkyWalking 补全 MQ 跨进程 traceId 传播
（当前是自定义 header 方案）；④ Redis Cluster 改造（当前单实例，Lua 脚本跨 slot 限制需要
hashtag 设计）。每条都给出验收标准（详见 16_项目进阶改造练习.md）。

### Q36. 如果 QPS 再涨 10 倍怎么办？

**满分答法**：分层作答——① 接入层：Nginx 多实例 + 限流（网关层令牌桶）；② 应用层：无状态水平扩展
（消费组自动均分队列、定时任务 Redisson 锁已就绪）；③ 缓存层：本地命中率已高（场景 F DB 零查询），
Redis 上 Cluster；④ 数据层：registration 按 user_id 分片（ShardingSphereShardingIT 已验证路由），
扩容双写迁移；⑤ 队列层：MQ 扩 Broker、消费线程加大。**强调：每一层当前设计已预留扩展点，
这是"单体优先"架构的底气。**
