## 练习 1：引入 Redis Cluster（★★）

**目标**：把单实例 Redis 改为 3 主 3 从 Cluster，识别并解决本项目所有"单实例假设"。

**步骤**：
1. 本机用 `redis-cli --cluster create` 搭 6 节点 Cluster（3 主 3 从，每主 1 slot 段）；
2. 改 `RedissonConfig`：`useSingleServer` → `useClusterServers`（nodeAddresses 列表注入）；
3. 盘点 Lua 的 Key 位置性：`StockRedisService.reserve` 的 5 个 KEYS
   （stock/members/meta/reservation/ratelimit 都含 activityId）——为跨 slot 访问，
   把 Key 前缀改成 hashtag 形式 `{activity:{id}}`（即 `RedisKeyConstants` 全量调整），
   保证同活动的所有 Key 落同一 slot；
4. `MultiLevelCacheService` 的 `activityInfo` Key 同样加 hashtag；
5. 跑集成测试（LuaOversellIT/IdempotencyIT/CancelConcurrencyIT）全部通过。

**验收标准**：
- [ ] `cluster nodes` 显示 3 主在线，同活动 Key `cluster keyslot` 值一致；
- [ ] 杀掉一个主节点，集群 failover 后报名链路自动恢复（记录恢复耗时）；
- [ ] LuaOversellIT 在 Cluster 下仍满足"恰好 10 条、库存不为负"；
- [ ] 复盘文档写清"为什么 hashtag 能保 Lua 原子性"。

## 练习 2：把本地消息表换成 RocketMQ 事务消息（★★）

**目标**：为报名确认链路实现事务消息版本，与本地消息表做一次真实对比（而非二选一）。

**步骤**：
1. 用 `producer.sendMessageInTransaction(msg, arg)` 实现事务消息发送（MessageDeliverService 旁新增
   `TransactionMessageService`，不要覆盖原实现）；
2. 实现事务监听器：`executeLocalTransaction` 里做 persistReservation（预留落库），
   `checkLocalTransaction` 回查 DB 中预留记录状态（PENDING_CONFIRM=提交、无记录=回滚）；
3. 造三类实验：①正常提交；②本地事务抛异常回滚；③提交后进程 kill（观察 Broker 反查）；
4. 输出对比表：投递轨迹可见性 / 重试可控性 / 代码复杂度 / 反查实现成本。

**验收标准**：
- [ ] 三类实验现象符合预期（半消息/回滚/反查后提交）；
- [ ] 对比表落盘（写进 `docs/performance/` 或复盘笔记）；
- [ ] 能口头回答：为什么主链路仍保留本地消息表（参考 MessageDeliverService 类注释的取舍）。

## 练习 3：接入 SkyWalking 分布式追踪（★★）

**目标**：把"自定义 TraceId（TraceIdFilter + MDC）"升级为标准 APM 链路，覆盖 MQ 跨进程。

**步骤**：
1. 本地跑起 SkyWalking OAP + UI（docker compose 追加两个服务）；
2. agent 挂到 campusflow-server 启动参数（`-javaagent:skywalking-agent.jar -Dskywalking.agent.service_name=campusflow-server`）；
3. 在 `TraceIdFilter` 里把 SkyWalking 的 traceId（`TraceContext.traceId()`）写入 MDC 与响应头
   （与自定义 ID 二选一或统一）；验证 RocketMQ 插件自动携带上下文到消费端；
4. 压一轮场景 A，在 UI 里打开一条报名链路：HTTP → Lua（redisson 插件）→ MQ send → 消费 → DB。

**验收标准**：
- [ ] UI 能看到完整拓扑图（应用/Redis/MySQL/MQ 节点）与单次调用链路；
- [ ] 日志里 %X{traceId} 与 UI 的 traceId 一致（grep 可对上）；
- [ ] 复盘：对比自定义方案与 APM 的差距（自动埋点/拓扑/采样率/性能开销）。

## 练习 4：前端摄像头扫码签到（★）

**目标**：组织者端用浏览器摄像头实时扫学生二维码核销（当前仅手输 token）。

**步骤**：
1. 前端安装 jsQR（`frontend/`，Vue3 + TS），在 organizer 签到页加"扫码核销"入口；
2. `getUserMedia` 打开后置摄像头，`requestAnimationFrame` 抓帧 → jsQR 解码 →
   解析 qrPayload JSON（`{"activityId","userId","token"}`，与 `CheckinService.buildTokenVO` 对齐）；
3. 解码成功即调用现有 `POST /api/v1/activities/{activityId}/checkin`（`ScanCheckinRequest`），
   成功后列表刷新 + 音效提示；连续扫码用去抖（同一 token 5 秒内不重复提交）。

**验收标准**：
- [ ] 手机屏幕出示二维码，笔记本摄像头 2 秒内完成核销；
- [ ] 同一凭证二次扫码命中"已签到"（后端 SETNX 三层防线生效）；
- [ ] 非 https 环境摄像头不可用的降级（手输 token）仍可用。

## 练习 5：MySQL 读写分离（★★）

**目标**：为查询类接口接入只读从库，理解"读已提交 vs 主从延迟"在本业务的取舍。

**步骤**：
1. MySQL 建主从复制（GTID）；
2. 两条路线任选其一：a) ShardingSphere-jdbc 的 `!READWRITE_SPLITTING` 规则（可挂进 sharding profile）；
   b) 自研 AbstractRoutingDataSource + 读事务注解路由；
3. 路由规则：`pageMyRegistrations/pageByActivity/getDetail` 等纯读走从库；
   报名/取消/确认/核销等写走主库；**注意**：报名后立刻轮询"我的报名"属于"读己之写"场景，
   轮询查询应强制主库（或带短暂主库亲和）；
4. 制造主从延迟（从库 STOP SLAVE），观察轮询查不到新报名的现象，再验证亲和策略生效。

**验收标准**：
- [ ] 慢查询日志/连接池监控证明读流量确实走向从库；
- [ ] "报名后轮询确认"链路在延迟 10s 时仍能正确显示（写己之读处理正确）；
- [ ] 复盘写出哪些接口可以容忍从库延迟、哪些必须主库。

## 练习 6：多实例部署验证（★★）

**目标**：单机跑两个应用实例 + Nginx 负载均衡，验证项目"多实例就绪"的三个机制。

**步骤**：
1. 同一 jar 起两实例（8081/8082，`server.port` 覆盖），Nginx upstream 轮询；
2. 验证①分布式锁：观察 `CompensationScheduler` 六任务的日志——同一时刻只有一个实例输出
   （另一实例 tryRun 抢锁失败静默返回）；
3. 验证②缓存广播：实例 1 上管理员改活动标题 → 实例 2 的 Caffeine 失效（观察
   CacheEvictConsumer 的 `[broadcast] 本地缓存失效` 日志出现在**两个**实例）；
4. 验证③消费组扩展：`rocketmq` 控制台看 consumption 差异——队列被两组均分；
5. 压一轮场景 A（两实例分流），对比单实例吞吐。

**验收标准**：
- [ ] 三个机制的验证证据（日志/截图）齐全；
- [ ] 能解释为什么本地消息表在多实例下依然正确（DB 幂等与扫描锁）；
- [ ] 找出一个多实例下仍未解决的问题并给出方案（例：日志分散需聚合、导出任务本地文件目录需共享存储）。

## 练习 7：限流升级——滑动窗口与令牌桶（★）

**目标**：替换/增强 `RateLimiterService` 的固定窗口，消除窗口交界突刺。

**步骤**：
1. 实现滑动窗口（ZSet 版）：`ZADD key now member` + `ZREMRANGEBYSCORE` 清界外 + `ZCARD` 判限；
   注意用 Lua 合并三步保原子（仿 reserve.lua 风格）；
2. 或接入 Redisson `RRateLimiter`（trySetRate + tryAcquire）实现令牌桶；
3. 用 JMeter 压固定边界（`-Jthreads=1 -Jloops=200` 连续请求跨窗口边界），
   对比固定窗口与滑动窗口的"实际放行数"曲线。

**验收标准**：
- [ ] 单测覆盖"交界处 2×limit 突刺"在滑动窗口下消失；
- [ ] 压测数据对比表（固定 vs 滑动）落盘；
- [ ] 能说清三种限流（固定/滑动/令牌桶）的成本与适用。

## 练习 8：热点库存分桶（★★★）

**目标**：单个活动库存从 1 个 Key 拆成 N 个分桶，验证 Lua 跨桶扣减的正确性。

**步骤**：
1. 预热时按 `capacity/N`（N=8）建 `stock:{id}:bucket:{0..N-1}`（沿用 hashtag `{activity:{id}}`）；
2. 改造 reserve：Lua 内 `RANDOM` 选桶 → 桶空则随机找其他桶（最多 N 次）→ 全空返回 0；
   保留 members/meta 语义不变；
3. 取消释放（cancel_release.lua）改成"随机回补一个非满桶"；
4. 对账口径改为 Σ 桶值；压场景 A 对比单桶（观察 Redis 单 Key 热点 CPU）。

**验收标准**：
- [ ] 不超卖四断言仍全部成立；
- [ ] `redis-cli --latency` 或 monitor 显示热点分散（无单 Key 长时间打满）；
- [ ] 复盘：分桶后"库存快照展示"（页面上剩余名额）如何聚合，代价是什么。

## 练习 9：活动名单异构索引表（★★）

**目标**：解决"按 activity_id 查名单在 user_id 分片下全路由广播"的代价（对应 10 讲测试 3）。

**步骤**：
1. 建表 `registration_by_activity(activity_id, user_id, status, registered_at, ...)`，
   主键 (activity_id, user_id)，按 activity_id 分片；
2. 在 `RegistrationConfirmConsumer` 与 `CancelReleaseConsumer` 的同事务里维护该表
   （或发独立 MQ 事件由新消费者落表——推荐后者，与主链路解耦）；
3. `pageByActivity` 改读异构表；补一致性校验：`stockReconcile` 同周期抽样比对主表/异构表行数。

**验收标准**：
- [ ] 名单查询路由到单分片（sql-show 日志证明）；
- [ ] 异构表与主表最终一致（对账抽样 0 漂移）；
- [ ] 复盘：为什么不在主事务里同步写异构表（解耦 vs 时延取舍）。

## 练习 10：WebSocket 候补晋级实时通知（★★）

**目标**：候选晋级后实时推送（当前是站内信 + 用户轮询），理解推送与轮询的共存策略。

**步骤**：
1. 引入 spring-boot-starter-websocket，JWT 握手鉴权（复用 JwtUtils）；
2. 前端登录后建立连接，订阅自己的通知通道；
3. `WaitlistPromoteConsumer` 消费晋级消息时同时推送（网关/直连按实例路由，
   或用 Redis pub/sub 广播给所有实例再本地路由——多实例下注意会话粘性）；
4. 保留轮询兜底（推送丢失时 30s 轮询仍是最终保障），前端做"推拉结合"。

**验收标准**：
- [ ] 晋级通知 1 秒内到达前端（比轮询快）；
- [ ] 断网重连后能补齐未读站内信（轮询兜底生效）；
- [ ] 复盘：推送通道的鉴权、重连、幂等三个工程点怎么处理的。

## 练习 11：深分页游标改造（★）

**目标**：消除 `LIMIT offset,size` 深分页代价（分片场景下是每分片都要拉前 offset 条）。

**步骤**：
1. `PageQuery`（campusflow-common）增加可选游标字段 `cursor`（上页最后一条的 registeredAt+id）；
2. `pageMyRegistrations` 构造 `WHERE (registered_at, id) < (#{cursor}) ORDER BY registered_at DESC, id DESC LIMIT size`；
3. `PageResult` 返回 nextCursor；前端"我的报名"改无限滚动加载；
4. 对照实验：造 10 万行数据，offset=50000 的页与游标页 EXPLAIN 对比扫描行数。

**验收标准**：
- [ ] 游标页扫描行数恒定 ≈ size，offset 页扫描 offset+size；
- [ ] 兼容旧 offset 模式（cursor 为空时走老逻辑）；
- [ ] 复盘：游标分页失去"跳页"能力，交互上如何取舍。

## 练习 12：分库分表扩容演练 2→4（★★★）

**目标**：模拟 registration 数据量翻倍后的不停机扩容（对应 10 讲 Q7 的落地）。

**步骤**：
1. 新建 `campusflow_ds2/ds3`，sharding.yaml 的 INLINE 表达式改 `ds_${user_id % 4}`
   （新逻辑库 `campusflow_sharding_v2`）；
2. 写迁移脚本：按 user_id 批次从老库读 → user_id % 4 路由写新库（幂等：INSERT IGNORE/唯一约束跳过）；
3. 双写阶段：消费端同时写新旧库（老库为准）→ 全量校验（count + 抽样 checksum）→
   读流量灰度切新库 → 停老写；
4. 全程记录各阶段数据一致性校验结果。

**验收标准**：
- [ ] 迁移脚本幂等可重跑（中断后继续不产生重复数据）；
- [ ] ShardingSphereShardingIT 的 4 分片版本（改写测试的 DDL 与 YAML）全部通过；
- [ ] 复盘：给出"什么时候必须做 4→8 再扩容"的触发指标（表行数/单库磁盘/连接数）。

## 附录 C · 改造时的安全红线

1. **不破坏既有测试**：任何改造后先跑
   `mvn -pl backend/campusflow-server test`，6 个 IT 全绿才允许提交；
2. **改造用分支/副本**：新逻辑与原实现并存（如 TransactionMessageService 不覆盖
   MessageDeliverService），对比完成再决定取舍——练习 2/7 都遵循此规则；
