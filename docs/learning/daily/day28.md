# Day 28 · JMeter 压测与性能优化

> 阶段十。主教材 `docs/learning/13_JMeter性能测试与优化.md` + `docs/performance/LOAD_TEST_REPORT.md`。

## 一、今天学习什么

1. **三场景设计思路**：
   - A（抢名额）：setUp 4 线程预登录 1000 人（BCrypt 慢哈希挡在突发外）→ tokens.csv →
     200 并发 × 5 循环突发；
   - B（一人一单）：同用户 50×20=1000 次 → Lua 返回码分布 1/7/992（成功/去重/限流）；
   - F（热点读）：200×50=10000 次详情 → 1677/s，DB 零查询；
2. **JMeter 工程细节**：vars 线程私有 vs props 全局（token 跨线程组必须 CSV 或 -J 注入）；
   JSR223 断言定义"合法业务码集合"（0|23001|23002|23003|23004|42901）；
   `-n` 非 GUI + `-l` jtl + `-e -o` HTML 报告；
3. **业务四断言**：DB 有效报名=名额 / COUNT=COUNT(DISTINCT) / Redis 库存=0 不为负 /
   confirmed_count 与 DB 一致；
4. **优化对比方法论**：一次一变量、同负载模型、jtl 归档、只报告真实测量值
   （报告明确不虚构提升百分比——工程诚实）。

## 五、面试自测（口头回答，答案要点）

1. **压测怎么设计的？**
   （三场景各测正确性/防重/读性能；setUp 预登录隔离 BCrypt 开销；200 并发分批避免
   压力机瓶颈；JSR223 断言定义合法业务码集合——错误率语义先行。）
2. **为什么 899 个"失败"错误率还是 0%？**
   （满员 23002 是业务正常态，HTTP 200 + 合法业务码；0% 指无系统级错误/非预期行为——
   场景 A 错误率的定义在断言脚本里。）
3. **P99=5ms 怎么做到的？**
   （997 个请求只走 Redis Lua（2.3ms 平均），不碰 MySQL；100 个成功者的落库由 MQ 异步
   完成——"输家零 DB 访问 + 赢家异步落库"的架构红利。）
4. **怎么证明你没超卖？**
   （业务四断言 + LuaOversellIT（30 抢 10）+ Lua 返回码分布（场景 B 三层防线各司其职）——
   三重证据链。）
5. **如果让你把系统再优化 30%，从哪下手？**
   （先归因：33.5ms 的 F 场景大头是拦截器/鉴权/INCR 固定开销——浏览量 INCR 异步聚合、
   鉴权结果短缓存；A 场景已接近 Redis 极限，优化空间在落库吞吐（消费线程 20-50 对照）
   ——先测后改，一次一变量。）

## 附一、知识点详解

**1. 三场景数字记忆卡（今天必须背下的六行）**
```
A: 999 请求 / 0% 错误 / 平均2.3ms / P99=5ms / 100成功+899满员 / 吞吐88(含登录)
B: 1000 次同用户 / Lua 1成功-3重复7次-4限流992次 / DB 1 条
F: 10000 次查询 / 吞吐1677/s / 平均33.5 P95=59 P99=96 / DB主表0查询
四断言: DB=100 / COUNT=COUNT(DISTINCT) / Redis=0 / confirmed_count=100
取舍: 200并发×5循环(压力机不越界); C/D/E用IT替代
诚实: 优化后基线, 不虚构提升百分比
```

**2. 为什么场景 F 平均 33.5ms 看起来"高"（归因思维）**
A 的 2.3ms 与 F 的 33.5ms 不是同一量纲：F 包含每请求的拦截器链/JWT 解析/
浏览量 INCR（一次 Redis 写）等固定开销，且 200 并发下 Tomcat 队列有排队。
**吞吐 1677/s 才是 F 的主角，延迟数字要结合负载解读**——面试时主动做这个区分
避免被"为什么读接口比写接口还慢"问懵。

**3. JSR223 断言的两个工程点**
①用正则匹配 code 集合而非精确值——业务合法结局是集合不是单值；
②失败消息截取前 120 字符——报告可读性。另外 Groovy 脚本在 JSR223 里
应缓存（脚本文件模式）避免每采样编译——高并发压测的断言脚本本身不能成为瓶颈。

**4. prepare_loadtest.py 走真实链路的深层原因**
approvePublish 触发预热（锁内按 DB 口径 preloadStock）→ Lua 才有 meta 可读；
同时布隆过滤器装载活动 ID。**绕过业务链路造数 = 制造一个"假系统"**——
压测的前提是被压对象与生产同构。

## 附三、面试加练（3 题）

**1. 压测会不会污染生产数据？怎么隔离？**
要点：单机验证用专用库/专用活动（prepare_loadtest.py 造的 capacity=100 活动隔离）；
生产全链路压测需要影子库/影子表 + 流量染色 + 数据打标——本项目阶段在
测试环境压测即可，知道影子方案是加分。

**2. 除了峰值压测，为什么要做长稳测试？**
要点：小时级持续负载才能暴露内存泄漏（堆缓涨）、连接泄漏（Hikari 占满）、
日志膨胀（磁盘打满）——峰值看正确性与延迟，长稳看"慢性病"。

**3. 压测报告给谁看？怎么分层？**
要点：给老板看结论表（三个数字）；给架构评审看场景设计与四断言；
给运维看观测数据（GC/MQ/慢 SQL）；给未来的自己看复现命令——
**一份报告四类受众**，本报告的章节结构正是如此。

**今日金句**：压测报告的含金量不在数字多漂亮，而在"业务断言是否全部成立"。
